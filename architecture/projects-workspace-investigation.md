# Проекты, чаты и рабочая директория агентов

Дата: 2026-09-23. Статус: исследование текущего рабочего дерева; реализация не начата.

Уточнение scope после обсуждения: самостоятельный агентный цикл и привязка задач/Workflow к проектам включены в эту же реализацию. Актуальные решения и полный план по файлам: `architecture/projects-agents-workflows-implementation-scope.md`. Ниже сохранено первоначальное исследование; его предложения отложить эти части заменены новым scope.

Запрос: сохранить обычные чаты, добавить проекты с именем и директорией, создавать чаты внутри проекта, сделать строки сайдбара компактнее и обеспечить работу моделей прежде всего в папке выбранного проекта. При необходимости доступ к другим папкам должен оставаться возможным.

Скриншот использован как визуальный ориентир: раскрываемый проект, вложенные однострочные чаты, ограниченное количество видимых записей и Show more. Это не требование переносить остальные возможности Codex.

## Вывод

Существующую систему сессий можно сохранить. Нужны новая сущность Project, связь session → project и единый контекст рабочей директории, вычисляемый сервером для каждого запуска. Основная сложность — согласованно применить его к файловым инструментам, командам, всем участникам генерации, просмотру файлов и памяти.

Добавление папок в сайдбар само по себе не меняет файловую область работы. Добавление пути только в prompt также не меняет действующие проверки доступа.

Отдельно: текущий движок не реализует полноценный цикл «модель запросила чтение → получила содержимое → продолжила рассуждение». Проектная привязка и самостоятельное исследование репозитория агентами — связанные, но разные объёмы работ.

## Предлагаемое поведение интерфейса

1. В зоне текущего Recent две вертикальные секции: обычные чаты и Projects. Когда обе заполнены, дать им примерно равные доли свободной высоты; пустая секция не должна занимать половину окна. Каждая секция прокручивается отдельно.
2. Рекомендуемый вариант: Recent содержит чаты без проекта. Чаты проекта показываются под ним, без дублирования. Если нужен общий список последних чатов, это можно добавить как отдельный режим позже.
3. Projects имеет кнопку `+`. Форма: имя, директория, «Выбрать папку», «Создать». Имя первоначально можно предложить по имени папки и разрешить изменить. Создание проекта регистрирует выбранную папку, не создаёт Git-репозиторий и не переносит её содержимое.
4. Строка проекта: раскрытие, иконка папки, имя, действия. В раскрытом виде — последние 5 чатов, «Показать ещё» и создание чата. Это соответствует предоставленному примеру.
5. Строка чата: только название, однострочное усечение, выделение активного чата, действия при наведении/фокусе. Дату и HTTP убрать из постоянной строки; оставить в подсказке/деталях. При необходимости канал Telegram/MCP можно обозначать компактной иконкой.
6. Ориентир высоты строки — 28–32 px вместо нынешней двухстрочной карточки. Точное уменьшение проверить на текущем масштабе шрифта; гарантировать ровно половину без визуальной проверки нельзя.
7. При открытии чата показывать проект и путь в шапке/настройках чата, чтобы рабочая папка была понятна до отправки сообщения.
8. `+` у Recent создаёт обычный чат, `+` у проекта — проектный. Верхняя New task использует явно выбранный проект; в UI должен быть виден этот выбор. Выбор пустого проекта не должен автоматически создавать пустой чат при каждом нажатии.
9. Сохранять раскрытые проекты и позицию прокрутки обеих секций между render(); существующий механизм сохраняет лишь прокрутку sidebar целиком. При смене чата сохранять черновик и прежнюю логику голосового ввода.

Текущие ensureSession(), обработчик new-session и deleteSessionById() автоматически выбирают/создают глобальную сессию. Все эти точки нужно обновить: после удаления последнего чата проекта показывать пустое состояние этого проекта, а не незаметно переключать рабочую папку.

## Данные и API

Предлагаемая минимальная схема:

```ts
interface Project {
  id: string;
  name: string;
  rootPath: string; // абсолютный канонический путь, проверенный сервером
  createdAt: string;
  updatedAt: string;
}

interface SessionSummary {
  // существующие поля сохраняются
  projectId?: string; // отсутствие = обычный чат
}

interface WorkspaceContext {
  projectId?: string;
  projectName?: string;
  rootPath: string;
  allowedDirectories: string[];
  outputDir: string;
}
```

- Добавить `src/projects/ProjectStore.ts`, `ProjectService.ts` и `src/api/projectControllers.ts`; хранить проекты в `appDataDir/projects.json`. Новая база данных для этого не требуется.
- В SessionIndexStore добавить get(id), projectId при создании и, если будет включён перенос чатов, отдельную операцию изменения принадлежности. touch() не должен терять связь с проектом или менять её по произвольным metadata запроса.
- Использовать готовые withFileLock/writeJsonAtomically из `src/utils/fileStore.ts` для изменяемых индексов. Текущий SessionIndexStore делает read-modify-write без очереди и обычный writeFile; создание чатов и проектов повышает значимость согласованных записей.
- Bootstrap возвращает projects рядом с sessions. Предлагаемые маршруты: GET/POST `/projects`, PATCH `/projects/:id` для имени, POST `/sessions` с `{ title, projectId? }`; GET `/sessions?projectId=...` при необходимости серверной фильтрации.
- При создании проверить непустое имя, существующую директорию, реальный абсолютный путь и доступность. Повторное добавление той же канонической директории лучше переводить к существующему проекту. Вложенные, но разные директории могут быть разными проектами.
- Отсутствующий/невалидный projectId — явная ошибка; отсутствие projectId у старой сессии — прежнее поведение. Недоступная папка проекта не должна вызывать скрытый откат к appRoot/outputDir.
- Старые сессии остаются обычными. История, настройки, вложения, идентификаторы чатов и расположение файлов истории не меняются. «Чаты внутри папки» означает организацию в UI и привязку к рабочей папке, а не запись переписки внутрь репозитория.
- Удаление/архивирование проекта не должно удалять его рабочую папку. Для первого этапа предпочтительно переименование и архивирование с сохранением связи чатов; физическое удаление истории и перенос чатов — отдельные явные действия.

В Electron добавить отдельный bridge `desktopProjects.selectDirectory()` и IPC-обработчик с проверкой окна/фрейма через существующий assertAppSender(). Для браузерного режима предусмотреть ввод пути на машине backend и его серверную проверку. Не считать загрузку папки через web file input получением рабочей директории backend.

## Единая рабочая папка на каждый запуск

Предлагаемая цепочка:

```text
sessionId
  → SessionIndexStore.get(sessionId)
  → ProjectStore.get(session.projectId)
  → проверка rootPath и построение WorkspaceContext
  → неизменяемый контекст запуска
      → основной агент, советники, debate-участники
      → файловые действия и команды
      → память и сохранённые результаты
```

WorkspaceContext нужно разрешать в общем слое выполнения, доступном CognitiveEngine и WorkflowRunner. Одного изменения HTTP controller недостаточно: Workflow и Telegram вызывают движок напрямую; HTTP/MCP используют processRuntimeInput(). SessionIndexStore сейчас создаётся после runtime в src/index.ts — потребуется перестроить внедрение общих store/resolver зависимостей, сохранив их при пересборке runtime из настроек.

Для проектного запуска rootPath/cwd/outputDir по умолчанию относятся к проекту, а allowedDirectories содержит его корень. Глобальные каталоги приложения не добавляются автоматически к разрешённым каталогам проекта. Для обычного чата сохраняются существующие значения.

Не менять process.chdir() или общий runtime.config при выборе проекта: runtime разделяют несколько чатов и фоновые задачи. FileTool/CommandTool должны получать область из input.context на каждый вызов. Учесть также fallback-заметки, scaffold, mkdir, выражение «текущая папка» и повторную регистрацию FileTool плагином.

Изменение выбранного проекта в UI не меняет уже начавшийся запуск. Для первого этапа можно запрещать перенос чата и изменение rootPath при активном запуске; переименование проекта этому не мешает. При смене папки между запусками нужна повторная проверка доступности и действующих разрешений.

## Доступ вне проекта

Уже имеющиеся режимы подходят для запроса пользователя, если считать workspace папкой данного проекта:

| Действие | Ask | Approve for me / Default | Full |
| --- | --- | --- | --- |
| Читать/перечислять файлы внутри проекта | Без отдельного подтверждения | Без отдельного подтверждения | Без подтверждения |
| Создавать/изменять файлы внутри проекта | Подтверждение | Без отдельного подтверждения | Без подтверждения |
| Удалять файлы | Подтверждение | Подтверждение | Без подтверждения |
| Обращаться к пути вне проекта | Подтверждение | Подтверждение | Без подтверждения |
| Выполнять команды | Подтверждение | Подтверждение | Без подтверждения |

Это таблица предлагаемых правил для проектных чатов на основе текущего AccessPolicy. Full сохраняет своё существующее значение; обязательное подтверждение внешнего доступа даже в Full означало бы изменение этого режима.

Обычное чтение папки проекта не требует отдельных запросов для каждой модели. Разрешение применяется к действию в чате; все его агенты наследуют одну область. Во внешнем запросе подтверждения показывать конкретный путь/операцию; подтверждение одной операции не должно автоматически добавлять весь диск или соседний проект в доверенную область.

Использовать canonicalPath/isWorkspacePath для `..`, symlink и несуществующих новых файлов через существующего предка. Проверить одинаковые правила в FileTool, Review, Open in editor, Reveal и WorkflowPathPolicy. Сейчас WorkflowPathPolicy и Reveal используют отдельные лексические проверки.

cwd команды определяет начальную папку, но не ограничивает возможности самого процесса. Существующая реализация — политика подтверждений приложения, а не sandbox ОС. Для данного запроса достаточно сохранить подтверждения команд и приоритет папки проекта; настоящая изоляция процессов была бы отдельной задачей.

Текущий new-session копирует настройки активного чата. При введении проектов нужно явно определить наследование: рекомендуется брать настройки последнего чата того же проекта либо defaults приложения. Полный доступ из последнего чата другого проекта не должен случайно становиться неочевидным default нового проекта.

## Контекст моделей и реальная работа с файлами

Добавить общий построитель контекста проекта: имя, корневая папка, база относительных путей, режим доступа и правило сначала искать в проекте. Передавать этот блок во все задачи, связанные с проектом: general/code, основной планировщик, подготовка заданий, советники, финальный синтез, support/attack/judge/advisors. Провайдеры и загрузчики моделей при этом остаются общими; отдельный экземпляр модели на проект не требуется.

Не принимать пути и права из текста модели, вложений или файлов проекта. Содержимое файлов — данные для анализа; оно не может переопределять выбранный пользователем проект и политику доступа.

Важное ограничение текущего кода: CognitiveEngine сначала вызывает handler() и получает ответ, затем executeTools(). Внутри одного запроса нет нового вызова модели с результатом чтения. Кодовые советники также не имеют собственного цикла файловых инструментов. Поэтому указание папки в prompt само по себе не даст поведение «сам найди нужные файлы, прочитай и исправь».

Варианты расширения, которые следует оценивать отдельно от сайдбара:

- Минимальный вариант: чтение явно указанных файлов до генерации через ту же политику, ограниченные размер/количество, содержимое передаётся основному агенту и нужным советникам. Не загружать весь репозиторий в prompt.
- Полный вариант: структурированные read/list/search запросы, авторизация, результаты инструментов в следующем шаге модели, лимит шагов и объёма, отмена и единая политика для подагентов. Для моделей без native tool calling потребуется валидируемый формат запросов.

FileSearchNodeExecutor можно использовать как источник существующей логики поиска/лимитов, но сейчас это узел Workflow, а не инструмент чата.

## Память и связанные запуски

Память необходимо учитывать в первом проектном релизе: закрыть доступ к файлам другого проекта недостаточно, если их сведения автоматически попадают в prompt из общей памяти.

Рекомендуемый default — долговременный поиск в пределах проекта, история сообщений по sessionId. Добавить project scope в ActorContext/параметры памяти; для world-partition использовать разделение по пользователю, каналу и проекту, либо на первом этапе отключать cross-session recall только для проектных чатов. Глобальные обычные чаты не должны автоматически находить новые записи из проектов.

Миграция старых записей и возможный перенос существующего чата требуют явной политики: история чата остаётся доступной, но нельзя просто переметить все общие воспоминания как относящиеся к новому проекту. Если разрешить перенос в первой версии, нужен согласованный перенос/переиндексация памяти либо чтение scope по актуальной принадлежности сессии.

LocalJsonMemoryAdapter уже ограничивает выборку сессией; проверить, что новая схема этого не расширяет. OpenMemoryAdapter сейчас не реализует query/recent и удаление сессии полностью — не считать проектный recall этого адаптера готовым.

Для Workflow, задач и расписаний возможны два честных объёма:

1. Первая версия только для чатов. В интерфейсе не обещать проектную область самостоятельным Workflow/расписаниям. При запуске узла агента с уже проектным sessionId общий resolver всё равно должен применяться.
2. Единая поддержка: projectId у Task/Schedule, WorkspaceContext в NodeExecutionContext и сохранённый контекст в WorkflowRun; file_search/file_write/command используют его вместо настроек конструктора. Противоречащие друг другу projectId и sessionId отклонять. После ожидания approval или перезапуска не подменять папку другим активным проектом. У узлов агента и отдельных workflow-инструментов также различается нынешний механизм approval — его нужно согласовать.

Telegram/MCP без привязки остаются обычными сессиями. При выполнении по существующему project sessionId область определяется сервером. Отдельные команды управления проектами в этих транспортах не обязательны для первого этапа.

Исходящий McpClientManager сейчас не подключён к executeTools() движка. Если в будущем предоставить эти инструменты агентам, проектную область нужно передавать и проверять отдельно: наличие project root у встроенного FileTool не ограничивает сторонний MCP-сервер.

## Порядок реализации

1. **Данные:** ProjectStore/Service, projectId, валидация пути, bootstrap/CRUD, совместимость старых чатов, очереди/атомарная запись индексов.
2. **Контекст:** resolver на каждый запуск, FileTool/CommandTool/Review/Reveal, prompts всех участников, область памяти. Это обязательная часть корректной проектной привязки.
3. **Интерфейс:** две секции, форма проекта, desktop picker, компактные строки, раскрытие/Show more, выбор/создание/удаление чата с учётом проекта и сохранение UI-состояния.
4. **Проверки:** интеграция с реальной временной файловой системой и визуальная проверка desktop/browser. Работа с реальными моделями нужна для проверки качества проектного контекста, но маршрутизацию/разрешения можно проверить детерминированно.
5. **Следующий объём при необходимости:** агентный цикл чтения/поиска, перенос чатов с памятью, настройки моделей по умолчанию на проект, проекты в Workflow/расписаниях. Если Workflow должен входить в первый релиз, перенести его контекст в этап 2.

Ни Git worktrees, ни перенос истории в рабочие папки, ни отдельная загрузка моделей для каждого проекта для описанной функции не требуются.

## Что проверить при реализации

- Создание проекта и чатов, перезапуск приложения, старые sessions.json без projectId, одинаковые/вложенные директории, путь с пробелами/кириллицей.
- Одновременные запросы проектов A и B с одинаковым относительным именем файла: запись и cwd остаются в соответствующих корнях; переключение UI не влияет на текущий запрос.
- Матрица Ask/Default/Full внутри и вне проекта, отмена/Stop, symlink и `..`; подтверждение не переносится на другую операцию.
- Файлы scaffold и fallback-результаты не оказываются неожиданно в appRoot или общем outputDir.
- Одинаковая область у основной модели, всех советников и debate-участников; недоверенные metadata/текст не меняют projectId/rootPath.
- Review, editor и Reveal открывают проектные файлы, не получают автоматического доступа ко всем проектам.
- Проектная память не смешивается с другим проектом или обычными чатами; история сохраняется при перезапуске, архивировании и предусмотренном переносе.
- Удаление последнего чата, пустой проект, сворачивание сайдбара, длинные названия, Show more, прокрутка, клавиатурный фокус, увеличенный шрифт, черновики/диктовка при переключении.
- Недоступная/перемещённая директория: понятная ошибка и возможность выбрать её заново, без автоматического выполнения в другой папке.
- Если включены Workflow/расписания: сохранение project root при waiting/resume/restart и отсутствие разрешений от постороннего проекта.

Существующая основа проверок: `test/chat-access.test.ts`, `test/review-panel.test.ts`, `test/chat-ui-regressions.test.ts`, `test/engine.test.ts`, `test/worldPartitionMemory.test.ts`, `test/workflowToolNodes.test.ts`.
